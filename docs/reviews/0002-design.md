## 1. 评审目标

- 设计必须逐条覆盖 P0 需求，且没有把安全责任留给"配置正确"。
- 信任边界、失败关闭点、残余风险必须写清楚。
- 关键决策要有可反驳的理由和备选方案。
- 设计中的外部事实（Agent 配置、MCP 形态、DSH 运行方式）必须来自一手资料或本地验证。

## 4. 安全评审意见

### 4.1 值得肯定的部分

- 不把 `HTTPS_PROXY` 作为唯一机制：这解决了 Node fetch/MCP 的兼容性陷阱。
- 模型流量走反向代理、MCP 走透明 TLS 的双路径，降低了 CA 兼容性对核心体验的影响。
- 占位符与凭据主机绑定，能阻止"把占位符发到攻击者域名"的朴素攻击。
- 失败关闭点写得具体，不是口号。

### 4.2 仍需在实现中证明的点

1. **Docker internal + 自定义 DNS**：沙箱必须能解析 `broker` 与白名单域名，且不能解析其他域名。
2. **Windows bind mount**：项目目录、只读配置目录、审计目录的读写权限与 UID 1000 的兼容性。
3. **DSH Web 端口/信任栅栏**：`--public-url`/`--trusted-host` 必须让浏览器通过。
4. **Codex 反向代理兼容**：base URL 是否按预期拼接 `/responses`。
5. **Claude Code `--strict-mcp-config`**：该 flag 是否存在；不存在则只使用 `--mcp-config`。
6. **系统信任包**：Rust/Go 客户端是否读取挂载后的 bundle。

这些点分别对应集成测试或用真实 CLI 的 `--version`/`--help` 冒烟验证；未通过前不得宣称对应需求完成。

### 4.3 需要向用户明示的取舍

- Docker 不是 VM；高风险代码建议独立虚拟机。
- Codex 的内层沙箱被关闭，外层 Cove 是唯一边界。
- 项目目录内明文密钥仍可被 Agent 读取；preflight 只做提醒/确认。
- 证书固定客户端不兼容。
- DSH Web 端口对本机开放。

## 5. 验证

本轮为文档，无自动化测试。人工验证：

- 设计 §12 的需求映射覆盖 FR-01..FR-12。
- 威胁模型 T1..T17 均至少有一条缓解和一条残余风险。
- ADR 的"备选方案"不是稻草人：正向代理、microVM、headless 都给出了具体放弃理由。
- DSH 的 Web 形态来自本机实际运行 `@deepseek-ai/dsh@0.2.1-rc.2`（`dsh web --help` 与启动日志），
  不是猜测。

## 6. 结论

通过，进入实现。实现阶段必须先关闭 R9/R10 与 4.2 的六项实测点；任何一项失败都要在设计/评审中
记录降级方案，不能静默妥协。
