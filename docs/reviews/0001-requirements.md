## 1. 评审目标

确认需求文档可以被直接用于设计与验收：目标可衡量、非目标明确、安全不变量可测试、范围没有
隐含的"以后再想"。本轮不评审实现（尚无代码）。

## 2. 检查清单

## 3. 发现与处理

| ID | 严重度 | 发现 | 处理 |
| --- | --- | --- | --- |
| R1 | 中 | 原文把 broker 写成"宿主侧代理"，但设计上它是独立容器；这会影响信任边界和密钥传递描述。 | 已改为"可信 broker 容器"，并在术语表中说明它与沙箱共享 internal 网络。 |
| R2 | 中 | FR-07 原文称"MCP server 在沙箱内运行"，不适用于 GitHub 等远程 HTTP MCP。 | 已区分本地 stdio 与远程 HTTP，两者出网都经 broker。 |
| R3 | 低 | 本地控制台端口"随机或固定 7777"不可验收。 | 已改为默认 7777、占用时回退随机端口并打印实际地址。 |
| R4 | 低 | 密钥出现位置未说明 broker 临时配置的删除时机。 | 已补充"读取后立即删除宿主临时文件，且不落在沙箱可见挂载"。 |
| R5 | 中 | DSH 的运行形态尚未确定（headless / Web / TUI），需求只写"支持 DSH"会不可验收。 | 保留为待决事项；设计文档必须选定一种并给出验收命令，否则该 P0 降级。 |

## 4. 范围与风险评估

- 需求覆盖面偏大，但 P0 被收敛为"单机、Windows、API Key、HTTPS MCP"四条边界，可在 v0.1 交付。
- 最大未被需求解决的风险是项目目录内的 `.env` 等文件：沙箱按设计可读整个项目。已列入风险表，
  实现需在启动前扫描并提示/拦截；该行为不改变"密钥不进入沙箱"的核心承诺，因为这类文件属于
  用户项目内容，不属于 Cove 管理的凭据。
- Docker Desktop 是硬依赖。若目标用户不愿安装 Docker，v0.1 无法满足；已作为假设记录，
  Podman/WSL 后端留待后续。

## 5. 验证

- README 的"目标形态"命令与需求中的 CLI 名称一致（`setup`/`secret`/`run`/`mcp`/`ui`）。
- 未在文档中承诺尚未设计的实现细节（例如具体镜像名、端口注入方式）。
